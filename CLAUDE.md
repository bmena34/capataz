# CLAUDE.md

Guidance for working on **capataz** with Claude Code. User-facing docs are in `README.md`; this file is the contributor/agent map: architecture, the dev loop, and the non-obvious gotchas.

## What it is

A terminal dashboard that supervises Claude Code agents running in tmux. **macOS-only** (it uses the macOS Keychain via `security` and `launchd` for the daemon). Pure Go, single binary with subcommands.

## Build / test / run

```sh
make build                                  # build ./capataz (local dev binary)
make install                                # build + sudo install to /usr/local/bin
make vet                                    # go vet ./...
make test                                   # go test ./...
go test ./internal/tui -run TestRenderNoPanic   # render regression (every size 1×1..80×50)
```

The binary is multiplexed by subcommand (`main.go`): default → dashboard; `daemon`, `hook`, `install`, `uninstall`, `status`, `logs`, `quit`, `config`, `issue`, `popup`, `attach`, `keybind`, `statusline`, plus three additive, daemon-free commands that back the external `capataz-herdr` herdr plugin: `issues` (standalone full-screen backlog viewer, `internal/tui/issueview.go`), `usage` (headless plan-usage gauge, `usage.go`), and `trust-dir` (pre-seed Claude folder-trust, `trust.go`) — and `issue waves` (JSON `ParallelSafe` plan). These add surfaces the plugin shells out to; they don't touch the daemon/tmux/dashboard.

**Dev loop — what to do after changing each component:**
- **daemon code** (`internal/daemon`): `go build -o capataz . && ./capataz restart`. The running daemon is a snapshot of the binary at launch.
- **dashboard code** (`internal/tui`): rebuild, then relaunch the dashboard. The **popup re-runs the binary fresh on every `prefix+g`**, so it picks up changes immediately; **sidebars** are long-lived and must be re-attached (`prefix+a`).
- **hook code** (`internal/hook`): rebuilt binary is re-exec'd on every hook call, so changes apply immediately. But **adding/removing a hook event** requires `./capataz install` (edits `~/.claude/settings.json`) **and** restarting any Claude sessions — hooks load at session start.

Debug: `./capataz status`, `./capataz logs` (app log at `~/.capataz/capataz.log`), `CAPATAZ_DEBUG=1` for verbose.

## Architecture

Data flows **hook → daemon → dashboard(s)**:

- **`internal/hook`** — `capataz hook <kind>` is invoked by Claude Code hooks. Reads the hook JSON from stdin plus `$TMUX_PANE`, sends a `proto.Event` to the daemon over a Unix socket (`~/.capataz/capataz.sock`). Must be fast and never block Claude.
- **`internal/daemon`** — one `launchd`-managed background process. Maps events → per-session state, polls plan usage centrally, prunes dead-pane sessions (5s sweep), and broadcasts `proto.Push` to every connected dashboard. Persists sessions + event history to SQLite (`~/.capataz/history.db`, `internal/store`).
- **`internal/tui`** — the Bubble Tea dashboard. Two launch modes: **popup** switcher (`CAPATAZ_POPUP=1`, transient — selecting quits) and **sidebar** (a normal pane — selecting switches without quitting). Several can run at once; all subscribe to the same daemon state. Acts on sessions purely through tmux (`tmux.go`: jump/reply/kill-window/rename/new-session/attach).
- **`internal/proto`** — wire types shared by all three (`Event`, `Session`, `Push`, `Usage`, state enum).
- **`internal/issues`** — reads the per-repo markdown backlog (`.scratch/<feature>/issues/NN-slug.md`) for the issue view. Pure Go, no daemon involvement: `Scan(repoRoot)` parses the `Status:`/`Type:`/`Blocked by:`/`Touches:` header lines; `SetStatus` rewrites the `Status:` line; `Bucket` collapses status to todo/doing/blocked/done; `ParallelSafe` derives waves of ready issues with pairwise-disjoint `Touches` and no blocking edge (`PathsOverlap` does the path-segment-prefix comparison; empty `Touches` ⇒ overlaps everything). Also hosts the `capataz issue` CLI (`Run`: claim/resolve/status/comment/list/new) — `new` serializes numbering per feature (`lockFeature`), `claim` is a locked compare-and-set (see the gotcha). The shipped skills call these, so any session (in any repo) that runs a capataz skill learns the commands from the skill body; bare `capataz issue` prints the authoritative subcommand list. Files are the source of truth — the TUI re-reads them, no daemon state.
- **`internal/worktree`** — thin `git worktree` helper (`Add`/`Remove`/`List`) plus `PrimaryCheckout(dir)` (the main working tree for any path inside a repo/worktree, via `git worktree list --porcelain`). Used so the `.scratch` backlog always resolves to the primary checkout even when a session runs in a linked worktree: `capataz issue new` and the TUI's backlog scan both route through it (behavior-preserving — a normal checkout is its own primary; the TUI resolves it only on cwd-change, never per tick). The dispatch side that actually *creates* worktrees is future work (`parallel-workflow` epic).
- Support: **`internal/paths`** (on-disk locations + `dev.capataz` launchd label), **`internal/config`** (`~/.config/capataz/config.json`), **`internal/install`** (hook wiring + launchd plist + skills copy), **`internal/logging`**.

Issue tracking is **TUI-read + a file-writing CLI + shipped skills** — no daemon, no proto types. The backlog is scoped to the selected session's repo. Two surfaces, split by role: the **sidebar** shows a concise read-only tracker (colored status dots + counts, sorted attention-first via `issues.Bucket`), rendered **only when `!m.popup`**; the **popup** (`prefix+g`) is the interaction surface where `i` opens the full-screen start-work view. Both read from a **cache** (`m.issueList`) refreshed off the render path — `syncSelectedIssues` runs on the tick and on selection change; `View()` never scans the filesystem. `issues.Bucket` is the single collapse from the open-ended `Status` vocabulary to `todo`/`doing`/`blocked`/`done`. Skills live in `skills/` (repo root), embedded via `//go:embed` in `embed_skills.go` and copied to `~/.claude/skills` by `capataz install`.

Shipped skills (`skills/`, embedded + installed): **`capataz-start`** (grill a fuzzy idea → lean `.scratch/<feature>/plan.md` → hands off to `capataz-splitter`; the pipeline's front door, a lighter take on mattpocock's grill-with-docs), **`capataz-splitter`** (plan → vertical-slice issues with predicted `Touches:`; replaces `/to-issues`), **`capataz-work`** (claim → implement → optional sanity-check → inline `capataz-comment-rot` docs pass for any change larger than a single small change → resolve; commits on its branch in isolated-worktree mode), **`capataz-triage`** (walk `needs-triage`/`needs-info` issues → grill for scope/criteria → promote to `ready-for-agent` with a `Touches:` line, or `wontfix`; the intake step review/security findings feed into), **`capataz-review`** (fresh-context correctness review → files findings as issues), **`capataz-security`** (fresh-context, OWASP-lens security review → files vulnerabilities as severity-tagged issues), **`capataz-investigate`** (diagnose a bug to root cause → files/annotates a ready-for-agent fix issue; diagnoses, does not fix — the diagnosis sibling of `capataz-review`), **`capataz-teach`** (explain a codebase area grounded in the real files → short in-terminal quiz; a lean operator learning tool), **`capataz-comment-rot`** (pre-PR docs hygiene pass over the change set: README judged for human readability, CLAUDE.md for agent signal-per-token, code comments for concision and truth — strips issue/PR references from comments; edits docs in place, never code; small fixes apply directly but large README/CLAUDE.md changes require the user's OK — hands-off runs file them as issue proposals instead; `capataz-doc-groomer` is its agent persona), **`capataz-drain`** (hands-off orchestrator behind `p`: loops over a feature's backlog dispatching `capataz-work` subagents in worktrees → merges each branch back → re-scans until drained), **`capataz-fix-conflict`** (fresh session that resolves a conflicted merge-back).

**Parallel dispatch** (issue view) is a **hands-off drain**, not one session per issue. `Touches:` + `issues.ParallelSafe` still derive the advisory `⇉` line, `space` multi-selects, and `p` opens the **confirm modal** (`modeParallelConfirm`) — but confirming (or `P`, or the bounded `w`) launches **one orchestration** (`dispatchDrain` → `launchOrchestration`) running the **`capataz-drain`** skill (`drainPrompt`, seeded with the selected feature + dispatchable issue numbers + `config.Parallel.MaxConcurrency`). Launch is **hand-to-current first**: when the client is attached to a managed session, the prompt is `reply()`'d into that pane — the drain runs as subagents under the operator's already-trusted claude (no fresh flagged process, no bypass-permissions screen) and shows as `⊂N` on that row; only with no attached managed session does it fall back to spawning a fresh sidebar-backed orchestrator (`newSessionWithSidebar` in the primary checkout). That orchestrator loops: scan ready issues → take a parallel-safe wave up to the concurrency cap → for each, `git worktree add` on a `capataz/<feature>-NN-slug` branch (`issues.DispatchBranch` naming) and spawn a **`capataz-work` subagent** in it (isolated-worktree mode, absolute issue path) → wait → merge each resolved branch into the base via git (clean lands; conflict spawns a **`capataz-fix-conflict` subagent**) → re-scan until the backlog drains. capataz shows the whole drain as **one row with a `⊂N` subagent count**, not N rows. No `install.TrustDir` / folder-trust pre-seeding is needed anymore — subagents run inside the orchestrator's session, so there's no fresh `claude` per issue to trust. Sessions capataz **spawns** with an opening prompt (fresh R/S reviews, fix-conflict, the drain fallback) can opt into `claude --dangerously-skip-permissions` via `config.Dispatch.SkipPermissions` — **default off**: permission prompts surface on the dashboard as NEEDS PERM instead, and `newClaudeSession` gates the flag on a non-empty prompt so the interactive `prefix+n` session is never flagged; subagents inherit whatever posture their session has. The operator-driven merge (`m` → `mergeReady`/`worktree.Merge`/`RemoveMerged`) and orphan-prune (`x`) remain for manually-created worktrees. Single-issue `n`/`h` dispatch and the `R`/`S` reviews are unchanged. `capataz issue comment` lets the review/fix-conflict skills annotate issues.

**Single-issue dispatch delegates to a subagent.** `issuePrompt` (used by both the new-session `n` and hand-off `h` paths) tells the receiving session to act as an orchestrator and spawn a subagent to run `capataz-work` — its main thread stays clean, and capataz shows the work as `⊂N` on that session's row. (The drain's worktree subagents run `capataz-work` directly — each is already isolated in its own worktree.) Because **subagents can't nest**, when `review.sanity_check` is on the sanity check runs at the *orchestrator* level (a second subagent), not inside the implementation subagent — the `capataz-work` 4b step skips itself when it detects it's the delegated subagent.

The **review loop** rests on the context distinction: a per-issue **sanity check** (opt-in `review.sanity_check`) runs as a **subagent** (in direct mode, inside the implementer's session; in delegated dispatch, at the orchestrator level) — `issuePrompt` appends the request, the `capataz-work` skill runs it before resolving. The full review (`R` in the issues view) runs in a **fresh session** (`startReview` → new session running `capataz-review`) precisely so it can't inherit the implementer's assumptions; it reviews the working/branch diff and files findings back as new issues via `capataz issue new`. The **security review** (`S`) is its sibling — `startSecurity` → a fresh session running `capataz-security`, an OWASP-lens audit of the same diff that files severity-tagged vulnerabilities as issues; both `R` and `S` route through the shared `startFreshReview` dispatch (they differ only in the skill prompt and the tmux session-name prefix). Subagent vs. new-session here is deliberate: a subagent's result must return to a caller (sanity check), a fresh review must *not* share context (full/security review). Dispatching a whole issue to a subagent means it shares the orchestrator's `session_id` and can't be its own dashboard row — historically we avoided it, but the **hands-off drain (`capataz-drain`) does it on purpose**: its `capataz-work` subagents show only as a `⊂N` count on the orchestrator row, a conscious trade of per-issue rows for one hands-off session instead of N. The distinction above still governs the review lanes.

## Gotchas (read before changing things)

- **Tracks only tmux sessions.** The daemon ignores a new session with no tmux pane, and the sweep drops sessions whose pane died. Task **subagents share their parent's `session_id`** (they're in-session sidechains) — so they can't be separate rows; the dashboard shows a `⊂N` count on the parent. The subagent-spawn tool is named **`Agent`** in current Claude Code (older: `Task`) — match both.
- **Popups have no `$TMUX_PANE`.** Anything that must work from the popup (e.g. new-session) must not depend on `TMUX_PANE` — gate on `$TMUX`. For client dimensions in a popup use `clientSize()` (`tmux list-clients`), not `display-message -p` (returns empty there).
- **tmux resizes panes proportionally.** The sidebar self-pins to its config width on a window resize (`pinSidebar`); new sessions are created at the client's real size so the split isn't 50/50.
- **Render must never panic.** Negative width/height math (slices, `strings.Repeat`) crashes the TUI, which closes its tmux pane (looks like "the sidebar disappeared"). Guard them; `TestRenderNoPanic` is the safety net.
- **Killing a session** sends `/quit` (graceful, fires `SessionEnd`) then `kill-window` after a grace period (tears down the sidebar too). If you're killing the session you're attached to, it hops the client to another managed session first. The `x`-confirm modal offers two graceful quits (`handleKillKey`): **`y` = quit & delete** — also `dismiss`es the still-live row so the daemon hard-deletes it in any state and **tombstones the id for 30s** so the dying process's in-flight `SessionEnd` can't resurrect it as a resumable row (`hub.dismissed`; a `SessionStart` lifts the tombstone since `claude --resume` reuses ids); and **`r` = quit (resumable)** — sends the same `/quit` and window teardown but *deliberately skips* `dismiss`, so the natural `SessionEnd` transitions the row to `StateEnded`/resumable (like a session that ended on its own) and `Enter` later relaunches it via `claude --resume <id>`. Either way the Claude transcript on disk survives (capataz never deletes it); the resumable row is just capataz remembering the id/label/cwd for one-keystroke resume. `SessionEnd` for an untracked id never creates a row, and a row is only retained as resumable if its transcript exists on disk (`resumableTranscript`) — a session that ends without one (e.g. the seconds-old throwaway id minted when an in-app `/resume` hands the pane to another conversation) is dropped, and the prune sweep evicts ended rows whose transcript later disappears.
- **launchd PATH**: the plist bakes the user's PATH (+ Homebrew) so the daemon can run `tmux`. Re-run `./capataz install` after PATH-relevant changes.
- **Usage gauge is unofficial.** The daemon reads the Claude Code OAuth token from the Keychain and calls `api/oauth/usage` (the endpoint `/usage` uses). URL + keychain item + interval + on/off are all in `config`; never hardcode them, and keep the "may change / disable-able" framing.
- **No external image/CLI deps** beyond the Go modules in `go.mod` (Bubble Tea, Lipgloss, modernc sqlite). Keep it dependency-light.
- **Issue file format is mattpocock-compatible, on purpose.** `.scratch/<feature>/issues/NN-slug.md` with `Status:`/`Type:`/`Blocked by:` header lines — same layout `/to-issues`, `/triage`, `/wayfinder` produce, so those planning skills interoperate. `Status` is free-form (triage roles *and* `claimed`/`resolved`); the parser (`internal/issues`) is deliberately tolerant and ignores unknown lines. Don't tighten it into a strict enum. `SetStatus` only touches the `Status:` line above the first `## ` section, so a "Status:" inside a `## Comments` thread is safe.
- **`claim` is a compare-and-set (the M1→M2 boundary), not a stamp.** `capataz issue claim` succeeds **only** from `ready-for-agent` → `claimed`; any other status errors (`already claimed` / `not claimable: <status>`). So it is **non-idempotent** — re-claiming an already-claimed issue fails; pass `--force` to override the state check (operator re-claim). The transition is atomic: read-status → check → write runs inside a per-issue-**file** O_EXCL lock (`lockClaim`, `<path>.capataz-claim.lock` — same pattern as `lockFeature` but keyed on the file, not the feature dir), and the status is re-read inside the lock, so N racing claims yield exactly one winner. This strictness is scoped to `claim` alone: `resolve`/`status` stay unconditional (resolve-from-claimed is normal, `status` is an operator override), and `SetStatus`'s general behavior is unchanged.
- **Starting an issue = one `claude "<prompt>"`.** The new-session path passes the opening prompt as claude's positional arg (via `newClaudeSession`'s `prompt`), avoiding send-keys boot-timing races; hand-to-selected uses `reply()`. If a claude build ever drops the positional-prompt behavior, only the new-session branch is affected.
- **Adding/removing a shipped skill** needs a rebuild (the `//go:embed skills` tree is baked into the binary) **and** `./capataz install` to re-copy into `~/.claude/skills`.
